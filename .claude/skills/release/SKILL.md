# release — release workflow

Execute these steps in order. Stop at the confirmation gate before pushing.

## 1. Preflight
- `git status --short` — warn if there are unstaged modifications beyond `package-lock.json` or `.env`.
- `git pull --rebase --autostash`.
- Latest tag: `git describe --tags --abbrev=0`.

## 2. Scope reconciliation
List commits since the latest tag with `git log --first-parent <latest-tag>..HEAD --oneline` and give a high-level summary. Include already-pushed-but-unreleased commits unless the user explicitly defers them.

## 3. Version bump
Apply to commits since the latest tag:

| Commit type     | Bump                                                |
| --------------- | --------------------------------------------------- |
| `fix:`          | patch                                               |
| `enhance:`      | patch                                               |
| `feat:`         | patch by default; minor if boundary met (see below) |
| breaking change | major                                               |

**Minor boundary** (either triggers minor):
- ≥ 2 `feat:` commits since the previous release, OR
- production-code line churn (insertions + deletions, excluding tests/docs/build) ≥ 2000 since the previous release.

Update `package.json` `version`. State the rationale briefly (e.g. "patch: fixes only" or "minor: 3 feats + cross-view UI change").

## 4. Update user-facing docs
Scan the commit range for user-visible behavior changes and update `USER_GUIDE.md` / `README.md` if any are now stale. Skip if nothing user-facing shifted.

## 5. Regenerate the changelog
`CHANGELOG.md` is generated by **git-cliff** from commit messages — do NOT hand-edit.

```sh
git cliff --tag v<version> --unreleased --prepend CHANGELOG.md
```

This prepends the new version section above the existing history; pre-4.0.0 entries are untouched. Review the diff. If an entry reads poorly:
- If the commit is **unpushed**, amend it (fix subject, body, or add a `Changelog:` trailer) and regenerate.
- If already pushed, accept it — the trailer convention will help next time.

## 6. Verify
```sh
npm install            # refresh lockfile after version bump
npm run lint
npm run typecheck
npx vitest run
npm run build
```
Fix any failures.
For more complex matters, commit the fix separately, or report back if next steps are unclear.

## 7. Commit + tag
- `chore(release): v<version>` containing the version bump + regenerated changelog. Amend the previous local commit only if it's a direct fixup.
- `git tag -a v<version> -m "v<version>"`.

## 8. Confirmation gate
Show: chosen version + rationale, changelog diff, tag name, `git log @{u}..HEAD --oneline`.

**Wait for explicit user confirmation before pushing.**

## 9. Push
```sh
git push
git push --tags
```

## Notes
- Reference relevant NIPs in commit messages when protocol behavior changed.
- Call out user-visible data loss (cache/persistence resets) prominently in the release notes preview.

# push — release workflow

When invoked, execute these steps in order. Stop and ask the user only at the explicit confirmation gate before pushing.

## 1. Preflight
- `git status --short` — warn if there are unstaged modifications beyond `package-lock.json`, `.env`, or `vite.config.ts`.
- `git pull --rebase --autostash`.
- Identify latest tag: `git describe --tags --abbrev=0`.

## 2. Scope reconciliation
Reconcile the pending release against all of:
- `CHANGELOG.md` `## [Unreleased]` section
- `git log --first-parent <latest-tag>..HEAD --oneline`
- `git diff --stat <latest-tag>..HEAD`

Ensure already-pushed-but-unreleased commits are included unless the user explicitly defers them. List commits since last version and give a high-level summary.

## 3. Version bump
Use the policy below, applied to commits since the latest tag:

| Commit type             | Bump                                                  |
| ----------------------- | ----------------------------------------------------- |
| `fix:`                  | patch                                                 |
| `enhance:`              | patch                                                 |
| `feat:`                 | patch by default; minor if boundary met (see below)   |
| breaking change         | major                                                 |

**Minor boundary** (either condition triggers minor):
- ≥ 2 `feat:` commits since the previous release, OR
- production-code line churn (insertions + deletions, excluding tests/docs/build) ≥ 2000 since the previous release.

Update `package.json` `version` accordingly. Include a short explicit rationale in the release notes (e.g. "patch for fixes only" or "minor: 3 feats + cross-view UI change").

## 4. Update user-facing docs and regenerate changelog
- Update `USER_GUIDE.md` / `README.md` if user-facing behavior changed.
- `CHANGELOG.md` is generated by **git-cliff** from commit messages — do NOT hand-edit. Regenerate it for the new version:
  ```sh
  git cliff --tag v<version> -o CHANGELOG.md
  ```
- Inspect the regenerated file; if entries are wrong, fix them by amending the underlying commit messages (subject, body, or `Changelog:` trailer) and regenerate — not by editing `CHANGELOG.md` directly.
- Routing reminder: `feat:` → Added, `fix:` → Fixed, `enhance:`/`perf:`/breaking → Changed. `refactor`/`test`/`docs`/`chore`/`style`/`build`/`ci` are skipped unless they carry a `Changelog:` trailer.

## 5. Lockfile + verification (release_prep matrix)
Run in order — all required:
```sh
npm install            # refresh lockfile
npm run lint
npm run typecheck
npx vitest run
npm run build
```
Stop on the first failure and report.

## 6. Commit + tag
- Commit the version bump + changelog as a single `chore(release): v<version>` commit (or amend if it's a direct fixup of the previous local commit).
- Create an annotated tag: `git tag -a v<version> -m "v<version>"`.

## 7. Confirmation gate
Show the user:
- chosen version + rationale
- final changelog diff
- tag name
- commits about to be pushed (`git log @{u}..HEAD --oneline`)

**Wait for explicit user confirmation before pushing.**

## 8. Push
```sh
git push
git push --tags
```

Report each commit/tag in the format: `✅ <hash> <type>: <message> (+<added> ~<changed> -<removed>)`.

- Document user-visible data loss (cache/persistence resets) prominently.
